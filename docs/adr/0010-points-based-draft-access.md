# ADR-0010: AI旅程ドラフト生成のアクセスをメール事前付与のポイント制にする

## ステータス

承認済み・実装済み（2026-07 に grill-with-docs で設計を確定し同日実装）。[ADR-0009](0009-ai-generation-cost-and-access-policy.md) の「サブスク導入時に `checkDraftAccess` を会員判定へ差し替える」の**第一段の差し替え**にあたる。

実装ファイル：モデル `src/lib/models/PointBalance.ts`・`PointTransaction.ts`／操作 `src/lib/points/points.ts`／アクセス判定 `src/lib/itineraryDraft/access.ts`（非同期化）／消費組込み `src/app/actions/generateItineraryDraft.ts`／残高API `src/app/api/itinerary-draft/access/route.ts`／フック `src/hooks/useDraftAccess.ts`／付与UI `src/app/admin/points/page.tsx`＋アクション `src/app/actions/points.ts`。

## コンテキスト

[ADR-0009](0009-ai-generation-cost-and-access-policy.md) の初版は、AI旅程ドラフト生成を環境変数 `ITINERARY_DRAFT_ALLOWED_EMAILS` の固定ホワイトリストで「限定者のみ」に絞っている。アクセス判定は [access.ts](../../src/lib/itineraryDraft/access.ts) の `checkDraftAccess()` に一点集約済み。

次の段階として、Android アプリのクローズドテスト協力者（33名）へ「お礼として一定回数の生成」を渡したい。ここで固定ホワイトリスト方式には限界がある。

- ホワイトリストは「使える／使えない」の2値で、**回数**を表現できない。
- 協力者はまだ本アプリのアカウントを持っていないことがある。**アカウント作成前に**、メールアドレスに対して回数を用意しておきたい。
- 本ADR時点で扱うのは前払いの「回数」であり、[ADR-0009](0009-ai-generation-cost-and-access-policy.md) が想定する将来のサブスク（月次クォータ）とは別レイヤーである。

ドメイン用語は [CONTEXT.md](../../CONTEXT.md) に定義した（[[ポイント]]／[[アズキ]]／[[消費レート]]）。本ADRはその実装・運用方針を定める。

## 決定

### 1. 通貨と単位（用語は CONTEXT.md が正）

- **ポイント**＝サービス内共通の抽象的な消費単位（残高）。**アズキ**＝そのユーザー向け表示単位で `1ポイント = 1アズキ` に固定（換算比は変えない）。
- **消費レート**＝機能ごとの消費数。初版は「旅程ドラフト生成 = 1ポイント」のみ。**生成が成功して受け取れたときだけ消費**し、失敗時は消費しない。用途をAI生成に縛らない抽象通貨とすることで、将来の別機能はレート表に1行足すだけで乗せられる。

### 2. 残高の一次キー ＝ 正規化メール（`email_verified` 必須）

- 残高は Auth0 の `sub`（ユーザーID）ではなく**正規化メールアドレス**をキーに保持する。`sub` はログイン方式（Google／メール）ごとに別物になり、アカウント作成前には存在しないため。メールキーなら「アカウント作成前の事前付与」と「ログイン方式の非依存」を claim 手順なしで自動的に満たす。
- 正規化は **`trim` ＋小文字化のみ**。Gmail のドット無視・`+`エイリアスの正規化は**しない**（対象33名にその形式は無く、過剰正規化は別人誤同定と複雑さを招く。ズレは管理者が手当て）。
- 成り済まし（他人のメールでアカウントを作り残高を奪う）を防ぐため、**`email_verified = true` のセッションのみ**ポイントを消費・表示できる。未検証は「メール認証を完了してください」で止める。
- **メールを提供しないログインは対象外。** メールをキーにする以上、`user.email` が空のセッションはポイント制に乗れない。`checkDraftAccess` は `email_verified` より手前で `!user.email` を見て「メールアドレスが取得できません」で弾く（安全側）。実測で **Facebookログインはメールを返さないことがある**（ユーザーが電話番号登録／メール共有を拒否。このとき Auth0 側では `email_verified` だけが true になり `email` は空という不整合が起きる）。該当ユーザーは**メール/パスワード等のメールを持つログインを使う**。Facebook 等でメールを取りに行くのは Facebook 側の権限・同意に依存して不確実なため、初版では追わない。

`checkDraftAccess` を次の順で判定する（**管理者判定は使わない**。管理者であることはアクセスと無関係）。

```
未ログイン              → 拒否
email_verified = false  → 拒否（メール認証を促す）
whitelist に一致         → 無制限で許可（消費しない）
それ以外                → 残高≥1 なら許可し成功時に1消費 / 残高0 は「アズキ不足」で拒否
```

- **whitelist（`ITINERARY_DRAFT_ALLOWED_EMAILS`）の意味を「限定者」から「無制限枠」に変更**する。当面は運営者本人1名のみを入れ、生成機能そのものを無制限に検証する。
- **管理者バイパスは設けない。** 管理者（例：妻）も残高制に従う。これは運営者自身がポイント消費・残高0・付与のUXを実地で検証できるようにするため（無制限にすると自分で挙動を試せない）。初回検証は「妻（管理者だが whitelist 外）に10ポイント付与」で行う。
- 残高判定のため `checkDraftAccess` は**非同期化**する（DBから残高を引く）。
- 公開時は whitelist ゲートを撤去し「残高一本」の形へ畳める（→ 保留）。

### 4. 消費は予約方式（LLM呼び出し直前に原子減算）

- **予約タイミングはLLM呼び出しの直前**（[generateItineraryDraft.ts](../../src/app/actions/generateItineraryDraft.ts) の生成ループ手前）。認証・入力チェック・feasibility は減算より手前に置き、そこで弾かれる失敗ではポイントを動かさない（「ポイントが動くのはAIが実際に動いたときだけ」）。
- 減算は `findOneAndUpdate({ email, balance ≥ 1 }, { $inc: { balance: -1 } })` の**条件付き原子更新**。これにより同時実行の二重取り（残高1で2件成立）も原理的に防げる。
- **失敗時は払い戻し**（`reserved && !committed` なら `$inc: +1`）。**クラッシュ時の払い戻し漏れは許容**（ユーザーが1回損。取引ログを見て管理者が手当て可能）。予約前に厳密な二相コミットは組まない。
- 内部リトライ（1回）は**同一予約の1回分**でカバーし、追加消費しない。
- UI側で生成中はボタンを無効化し多重送信を抑止する。

### 5. 保存 ＝ 残高 ＋ 取引ログ（別コレクション）

```
pointBalances:      { email(unique index), balance, createdAt, updatedAt }
pointTransactions:  { email, type: 'grant'|'consume'|'refund', amount,
                      reason, actor, createdAt }
```

- ポイントは実質お金なので、トラブル対応・クラッシュ払い戻し漏れの手当て・将来サブスク移行時の整合のため、**取引ログをDBに正本として持つ**。PostHog（[ADR-0005](0005-posthog-replaces-google-analytics.md)）は分析用でありお金の帳簿には使わない。
- 取引ログは残高ドキュメントへの埋め込みではなく**別コレクション**（無制限な配列肥大を避ける）。33名・低頻度なので量は小さい。

### 6. 付与は管理者UI（$incで加算）

- `src/app/admin/points/` あたりに最小の付与フォーム（**メール／ポイント数／理由**）を置く。Server Action で `pointBalances` を更新し `pointTransactions` に `grant` を記録。妻の「使い切って再付与」テストもここで回す。
- 付与は**上書き(set)ではなく加算($inc)**。初期付与も補充も同じ加算で扱え、補充時に残高を消す事故を避ける。
- **冪等（二重付与防止）は初版では省略**（妻1名・手動で目視確認）。33名バッチ付与を作るときに `batchId + email` のユニークキーで足す（→ 保留）。

### 7. 有効期限 ＝ 無期限

前払いの謝礼という好意ベースの文脈で期限は逆効果。33名・1回2円で未使用分の負債も無視できる。月次リセット等は将来サブスクのクォータ設計に委ね、ここでは持ち込まない。

### 8. 表示（UX）

- 生成ページに「**残り N アズキ**」を表示。無制限枠のユーザーには数値でなく「**無制限**」。
- 残高は消費で変動するため、**生成成功のレスポンス（`GenerateDraftResult`）に更新後の残高を載せて即時反映**する。初回値は `/api/auth/me` から取る（`useDraftAccess` を拡張。[useDraftAccess.ts](../../src/hooks/useDraftAccess.ts) の1回キャッシュだけだと消費後にズレる）。
- 残高0は生成ボタンを無効化し「**アズキが不足しています**」と案内（管理者連絡等の導線。公開時は購入/申請導線に差し替えられる場所にする）。
- 付与通知メールは初版では作らない（妻へは別途連絡で足りる。公開時に検討 → 保留）。

## 理由

- **回数を表現でき、アカウント作成前に付与できる**方式が、クローズドテスト協力者へのお礼という要件を直接満たす。固定ホワイトリスト（2値）では表現できない。
- 正確性をコードに寄せる（原子減算・条件付き更新・取引ログ）方針は、[ADR-0008](0008-itinerary-draft-generation-architecture.md) の「構造の正しさはコードが持つ」思想と一貫する。
- `checkDraftAccess` 一点集約（[ADR-0009](0009-ai-generation-cost-and-access-policy.md)）を保ったまま条件を差し替えるので、将来サブスクへも「月次ポイント自動付与型」「会員=無制限枠型」のどちらでも乗せられ、将来を縛らない。

## トレードオフ

- **メールキーは成り済ましの余地**を持つ。`email_verified` 必須で緩和するが、Auth0 の検証運用に依存する。
- **概念が2段（whitelist＝無制限枠 ＋ 残高制）**になり、単純な残高一本より1つ多い。これは公開までの安全弁で、公開時にゲートを畳んで解消する前提。
- **クラッシュ時に払い戻し漏れ**が起きうる（ユーザーが1回損）。二相コミットの複雑さを避けた対価で、取引ログで事後手当てする。
- **冪等な付与を初版で持たない**ため、33名バッチ時に二重付与を防ぐ仕組みを別途足す必要がある。

## 保留（後日）

- 33名へのバッチ付与と、その冪等キー（`batchId + email`）。
- 公開時の whitelist ゲート撤去（「残高一本」への収束）と、残高0時の購入/申請導線・付与通知メール。
- サブスク統合の具体方式（月次ポイント付与型 vs 会員=無制限枠型）。[ADR-0009](0009-ai-generation-cost-and-access-policy.md) が未決とする**課金の置き場所（Web/Stripe vs Android/Play）とセットで決める**。

## 注意

- `checkDraftAccess` は生成機能の**唯一のアクセスゲート**であり続ける。残高判定・予約・払い戻しの整合を、実装の都合で別経路に散らさないこと。
- ポイントは実質お金である。**予約→払い戻しの対応**と**取引ログの記帳**を崩さないこと。崩すと「使ったのに減らない／使ってないのに減る」が静かに発生し、原因追跡もできなくなる。
- 無制限枠（whitelist）を安易に広げないこと。1件広げるごとに、その分だけ従量コストが公開課金ゼロの前提（[ADR-0009](0009-ai-generation-cost-and-access-policy.md)）から漏れる。
