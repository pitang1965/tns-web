# ADR-0008: AI旅程ドラフト生成を「実在スポット背骨＋制約付きLLM生成」で構成する

## ステータス

承認済み・実装済み（2026-07、`9f21107` 実装 / `ff7286d` 不具合修正 / 末尾「追記（2026-07）」の⓪①④アンカー・off-peak・方式Qを `validate.ts`・`prompt.ts` に実装）。追記のうち②（泊地重複の最狭除去）のみ、実測で重複が再発した場合に追加する方針で**現状は未実装**。

## コンテキスト

LLM API を活用した機能として、自然言語の希望から旅程の下書きを生成する機能を計画している。ドメイン用語は [CONTEXT.md](../../CONTEXT.md) に定義済みで、本ADRは次の概念を前提とする。

- **旅程ドラフト**：AIが提案として生成する、まだ保存されていない旅程の候補。ユーザーが編集・承認して初めて旅程になる。
- **目的地／経由地**：ユーザーが行きたいと指定する場所（観光地・温泉街など）。順序付きで複数指定できる。
- **泊地**：各夜に眠る場所。実在の車中泊スポットの中からシステムが提案する。

素朴に「LLMに旅程全体を生成させる」設計には致命的な問題がある。

- LLMは正確な緯度経度を出せない。全体ルート検索・地図表示という本アプリの中核機能はすべて座標に依存する（[CONTEXT.md](../../CONTEXT.md) の全体ルート検索等）ため、LLMが創作した座標では地図が壊れる。
- 本アプリは約1,900件の実座標付き車中泊スポットDBという資産を持つ（[ADR-0006](0006-versioned-mobile-api.md)）。「実際に泊まれる場所」を出せることが、汎用の旅程生成AIとの決定的な差別化になる。泊地が創作だと「行ったら泊まれない」＝プロダクトとして致命的。
- 診断機能は車高・全長から泊まれないスポット種別を除外し、ペルソナと推奨種別を出す（`src/data/schemas/diagnosisSchema.ts`）。この既存ロジックが泊地候補のフィルタにそのまま使える。

## 決定

旅程ドラフト生成を、次の分担で構成する。

1. **泊地の背骨は実在DB由来（モデルA）**：各夜の泊地は必ず実在の車中泊スポットDBから選ぶ。LLMに泊地を創作させない。

2. **コードが候補プールを用意し、LLMが選択・生成する（案3）**：
   - 経路は、出発地・目的地（複数・順序付き）・出発地への復路（往復を既定）を直線で結んだ折れ線とする。距離は既存の Haversine（`src/lib/utils/distance.ts`）に**回り道係数**を掛けて走行距離を近似する。道路距離API（Mapbox Directions等）は使わない（[ADR-0009](0009-ai-generation-cost-and-access-policy.md) のコスト方針に従い将来の最適化とする）。
   - 折れ線に沿って各夜の目標地点を配置し、その周辺の実在スポットを「回廊内・1日の走行距離内・車で泊まれる種別・好み種別」で絞り、**1夜あたり3〜8件の候補**に落とす。ランキング（近さ＋ペルソナ適合）はコード側で決定的に行う。
   - LLMには①ウェイポイント列、②各夜の候補スポット（`spotId`＋属性）、③ペルソナ・制約を渡す。LLMは構造化出力（tool use）で、各夜の `chosenSpotId`（**必ず候補リストのidのいずれか**）と日中のアクティビティ列（観光地・入浴等）を返す。

3. **三重の決定的検証層**：
   - `chosenSpotId` が候補集合に存在しなければ棄却する。泊地の座標・名称はLLM出力ではなく**DBの正データで上書き**する（LLMは選ぶだけ、値は信じない）。
   - 日中のアクティビティの場所名は Mapbox Search Box API（既存の場所名→座標解決。`src/components/itinerary/forms/PlaceNameAutocomplete.tsx` で利用中）でサーバー側に座標解決する。目的地・都道府県で経路周辺にバイアスし、**低信頼・曖昧なら座標を null にフォールバック**する（推測で誤座標を置かない）。泊地近傍の入浴施設は、スポットDBが持つ `nearbyBathCoordinates` からDB由来でグラウンディングできる。
   - 全体を最終的に既存の `clientItinerarySchema` 相当で Zod 検証する。

4. **無理筋な入力・候補ゼロの扱い**：
   - 実現不可能な入力（総経路距離÷泊数が1日の走行距離を大きく超える）は、**LLMを呼ぶ前にコードで事前警告**し、泊数増・距離増・目的地削減を促す（LLMコストを使わずに弾く）。
   - ある夜の泊地候補がゼロなら、回廊バッファ拡大→距離超過許容と段階的に緩め、それでも無ければその夜の泊地を null にして注記を付け、旅程全体は部分成立させる。
   - LLM出力が検証を通らない／候補外idを返す場合は、エラー内容を添えて1回だけ再試行し、それでも駄目なら明確なメッセージで失敗する（無限リトライしない）。

生成された旅程ドラフトは、既存の旅程表示コンポーネント（地図＋日程表示）でプレビューし、「保存」で初めてDBに書き込む。保存した時点で通常の旅程となり、承認したユーザーが作成者となる。「AIが生成した」フラグは旅程スキーマに追加しない（必要なら生成イベントを PostHog で計測。[ADR-0005](0005-posthog-replaces-google-analytics.md)）。

## 理由

- 正確性の担保をコードに寄せることで、LLMがどう振る舞っても破綻しない。候補は必ず実在・到達可能・その車で泊まれる・好みに合う。
- 既存資産（Haversine距離、Mongoの地理クエリ、診断ロジック、Mapbox Search Box、Zodスキーマ、旅程表示コンポーネント）をほぼそのまま再利用でき、新規に持ち込む外部依存が少ない。
- 「retrievalで候補を絞り、LLMが制約下で選択・生成し、決定的に検証・棄却する」構成は、単なるプロンプトラッパーより堅牢で、実装難度とのバランスが良い。

## トレードオフ

- 泊地選定は純粋なLLM生成ではなく「DB検索＋制約充足」のロジックを要し、実装の重心はそこに移る。
- 直線＋回り道係数は山間部で誤差が出る。道路距離は精度向上の将来オプションとして [ADR-0009](0009-ai-generation-cost-and-access-policy.md) に委ねる。
- 完全エージェント型（LLMが検索ツールを繰り返し呼んで自律的に組む）に比べ、経路の探索的な工夫は弱い。これは将来の発展形として保留する。

## 注意

泊地はハルシネーション防止の要である。「LLMが候補idから選ぶだけ／泊地の値はDBの正／出力は最終的にZod検証」という三重防御を、実装の都合で崩さないこと（例：LLMに座標や新規スポットを直接生成させる、検証をスキップする）。崩すと「実際には泊まれない場所」が旅程に載る。

## 追記（2026-07）: 構造アンカーのコード所有と off-peak 時刻

初版実装（`9f21107` / `ff7286d`）を動かして得た知見から、本ADRの「構造の正しさはコードが持つ」原則を **泊地から「出発地からの出発」「出発地への帰着」へ拡張**する。モデルは初版据え置き（`claude-haiku-4-5`、[ADR-0009](0009-ai-generation-cost-and-access-policy.md)）で、安定性はモデル増強ではなくコードの決定論で担保する。

**背景（モデル任せの綻び）：** 実測で次の3症状が出た。いずれも「出発地へ戻る」という構造要素の置き場所を LLM に委ねていたことが根因で、Haiku をより賢いモデルに替えても発生頻度が下がるだけで無くならない（本ADRの「LLMがどう振る舞っても破綻しない」約束に反する）。
- ① 最終日に帰着が**出ない**（LLMの出し忘れ）。
- ② 泊地と同じ場所が日中アクティビティにも出る**重複ピン**。
- ④日目リーク：4泊5日で**出発地が4日目にも登場**（帰着系の早出し。プロンプト「帰着は最終日のみ」の違反）。

**決定：**

1. **構造アンカーはコード所有**：泊地（既存）に加え「出発地からの出発」「出発地への帰着（往復＝`roundTrip=true` のときのみ）」も構造アンカーとし、その**身元（存在・名称・座標）はコードが確定**する。LLMにアンカーを創作させない。片道（`roundTrip=false`）は最終目的地で旅が終わるため帰着アンカーを挿入しない。

2. **時刻は LLM 所有（"身元はコード・時刻は LLM"）**：アンカーの `startTime/endTime` は LLM が off-peak な現実値を提案する（車中泊旅は渋滞回避が本質。初日は午後・夜発、深夜〜早朝着も想定内、宿泊翌朝から観光、最終日は早めに帰宅）。走行時間の土地勘は LLM の方があり、時刻は多少ズレても構造を壊さないソフト領域のため。コードは順序等を検証する。→「構造＝コード／ソフト（時刻）＝LLM」の線を、日中アクティビティだけでなくアンカーにも適用する。方式は **(Q) 識別子はコード・時刻は LLM**：LLM に出発/帰着を off-peak 時刻付きで書かせ、コードが名称・座標を出発地の正データで上書きし、時刻は採用し、正規位置以外の出発地一致アクティビティは除去し、最終日に帰着が無ければ挿入する。初日の出発時間帯はユーザーが3択（朝/午後/夕方・既定=午後）で選べる（`departureTimeOfDay`）。UIはラベルのみで、内部の目安時刻（朝≈9時/午後≈13時/夕方≈19時）をプロンプトに渡し、LLMが初日の観光量ごと調整する（夕方発＝初日は移動主体、朝発＝初日から観光可）。時刻は目安で、生成後は既存の時刻ずらし機能（`TimeShiftDialog`）で微調整できるため精密固定はしない。

3. **構造アンカーの決定論的保証（⓪①②④）**：
   - ⓪（出発地の欠落）→ 1日目の先頭に出発アンカーを**必ず挿入（prepend）**する。実測（出発地=イオンモール武蔵村山）で挙動が**非決定的**だった：2泊の回はLLMが「出発地を出発 → 最初の目的地に到着」を1アクティビティに畳み込みピンを到着先に置いたため出発地のピンが立たず、4泊の回はLLMが素直に出発を出したため全体の最初と最後に出発地が出た。同じコードで結果が割れる＝モデル任せの綻びであり、「今は出ている」も次の生成で畳み込まれれば再発する。現行の [validate.ts:252-254](../../src/lib/itineraryDraft/validate.ts#L252-L254) の「先頭が座標 null のときだけグラウンディング」では畳み込みを取りこぼす。よって**null補正ではなく挿入で保証**し、"たまたま出る"を"必ず出る"に変える。出発アンカーの時刻は**1日目・先頭LLMアクティビティの startTime を継承**（方式Qの時刻をLLMに委ねる方針と整合し、畳み込み・分割どちらでも破綻しない）。プロンプトでは1日目を独立した「◯◯を出発」で始め、到着に畳み込ませない。
   - ①（帰着欠落）→ 往復なら最終日末尾に帰着を**必ず挿入**（[validate.ts](../../src/lib/itineraryDraft/validate.ts) の最終日補正を「補正」から「保証」に格上げ）。
   - ④（帰着の早出し）→ 正規アンカー位置以外に出た**出発地一致アクティビティを除去**。出発地はユーザー入力の確定値なので判定が明快（曖昧さなし）。
   - ②（泊地重複）→ まずプロンプトで抑止し**実測**する。残る場合のみ**最狭の除去**（`chosenSpotId` のスポットと**名称一致 かつ 座標超近接（〜30m）**の日中アクティビティのみ）を足す。汎用の近接削除はしない（泊地近傍の入浴施設など正当な近隣スポットの巻き添えを防ぐため）。

4. **off-peak は「時間」であって「距離」ではない**：off-peak は走行**時間帯**をずらして渋滞を避けることで、走行**距離**を減らすことではない（22時着も想定内、初日・最終日に多く走る人もいる）。よって `dailyDistanceKm` は**全日共通の上限**として据え置き、日ごとの走行距離の重み付けはしない。[candidates.ts](../../src/lib/itineraryDraft/candidates.ts) の均等配置・[feasibility.ts](../../src/lib/itineraryDraft/feasibility.ts) の距離モデルは**変更しない**。プロンプトの「1日の走行距離の**目安**」は実体に合わせ「**上限**」と表現する（中間日を短くしやすくするため）。

**保留（後日・非ブロックのUX改善）：** feasibility は「物理的に走れないか」だけを弾く（[feasibility.ts](../../src/lib/itineraryDraft/feasibility.ts)、許容 `1.15`）。実測で、本来4泊が快適な経路を2泊で入力しても `perDayKm≈247 ≤ 250×1.15` で**通ってしまい、観光の余裕が無いカツカツの旅程**が生成された。将来、実現可能でも `perDayKm` が上限に近い（例 >0.8×）ときは「この距離なら◯泊がおすすめ」と**非ブロックで推奨泊数を提示**する（`suggestedNights` の計算を再利用）。ブロックはしない（沢山走る人を妨げない）。リリース必須ではなく、⓪①②④のアンカー修正の後に回す。

**注意（拡張）：** 「出発地の存在」「帰着の存在」「出発地が正規位置以外に出ないこと」「泊地の非重複」は、プロンプトの"お願い"だけに委ねず**コードで保証**すること。モデルを賢くして頻度を下げる対処は、この保証の代替にならない。
